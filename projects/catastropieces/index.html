Catastropieces

USC Advanced Games Project

Lead Engineer, USC Advanced Games Project·2017–2018

Unity · C# · Havok Physics · PhysX · JSON

Links:itch.io ↗·GamesBeat ↗

Catastropieces was my USC senior capstone, built through the Advanced Games Project (AGP) program over the 2017–2018 school year. It’s a 3D point-and-click puzzle game about building Rube Goldberg machines to make art. You play an artist who’s out of inspiration until they decide the whole room is the canvas. Each level is a different room full of everyday objects (more than 30 types in all), and you rotate the room, zoom in and out, and arrange those objects into a chain reaction that ends with paint splashing onto a canvas. When a machine fails, you adjust it and run it again.

The game was released free for Windows on itch.io, where it was featured on the front page and passed 1,500 downloads in its first month. It was also shown at the USC Games Expo and covered by GamesBeat.

Why the physics mattered

The whole game is a physics simulation. The player doesn’t control a character; they set up initial conditions and watch them play out. That makes the physics the core game mechanic, not a background system. A machine is a long chain of collisions, rolls, tips, and falls, and a tiny difference early in the chain (a slightly different contact point, a ball landing a fraction of a degree off) grows into a completely different outcome by the end.

For a puzzle game, that’s a serious problem. If a player builds a working machine and it fails the next time they press play, the game feels broken. If a designer tunes a level’s solution and it only works some of the time, the level can’t be shipped.

What I worked on

Lead engineer: led a team of five engineers. I assigned tasks, ran code reviews, wrote and maintained the technical documentation, and was the engineering point of contact for the art and design teams.

Deterministic physics: much of my work went into making the simulation as deterministic as possible, so the same setup gives the same result every time it runs. That meant the solution a designer tuned was the solution a player would find, and a machine the player built kept behaving the same way while they kept iterating on it.

PhysX to Havok migration: partway through development, I moved the project’s physics from Unity’s built-in PhysX to Havok, bringing over the game’s objects and existing levels to the new engine.

Destruction: fracture assets were part of the gameplay. Objects that shatter are part of the machine, so their pieces had to break and scatter predictably enough for players to plan around them, not just look good.

Engine tools: built editor tools so engineers and designers could set up and iterate on levels faster.

Save system: built a save format that stored the game state as JSON metadata embedded inside a PNG image, so each save file was also a picture of the player’s machine.
